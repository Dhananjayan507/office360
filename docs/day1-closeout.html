Why these particular gaps mattered. They are not loose ends — they are the contract every later day is written against. Day 6 onward, every handler in every module returns through this envelope. Get it wrong now and twenty modules inherit it.

1

The typed error set

The plan's rule is one sentence: handlers must never build status codes directly — they return a typed error and httpx maps it. That exists so one kind of failure cannot be a 400 in one module and a 422 in another.

Create api/internal/httpx/errors.go. The heart of it is the kind list and the single map:

Then the error type itself. cause is unexported deliberately — it reaches the logs and never the client:

Plus one constructor per kind — Validation(msg, fields), NotFound(msg), Conflict(msg), RuleViolation(msg), Internal(cause) and the rest.

One deliberate deviation from the plan. Its list stops at 429 and has no 405. Without one, chi's default method-not-allowed handler answers in plain text and bypasses the envelope entirely — so a client parsing JSON gets a surprise. KindMethodNotAllowed closes that hole. It extends the principle rather than breaking it.

Unknown kinds fall to 500, not 200. If someone adds a kind and forgets the map entry, the failure is loud instead of a success response with an error body.

4

The config gate

The plan's end-of-day check is explicit: deleting JWT_SECRET stops the server with a clear message. There was no JWT_SECRET anywhere in the project, so that test could not pass.

Add it to the environment template too:

Testing this is harder than it looks. Setting $env:JWT_SECRET = "" in PowerShell does not give the child process an empty variable — Windows drops empty values, so the variable arrives unset. godotenv then loads the repo's .env, finds a perfectly good secret, and the server starts. The test appears to fail when the code is right.

Run the binary from a directory with no .env above it, and use Remove-Item env:JWT_SECRET rather than assigning an empty string.

Health keeps its own status code, on purpose. It calls httpx.Write with an explicit 200 or 503 rather than returning a typed error, because there the status is the answer — a monitor reads it without parsing the body. That is the documented exception, not a loophole.

Ordering trap in update: the pgx.ErrNoRows check must come before the constraint check. An update against a missing id is a 404, not a 400.

7

The folder tree and the README

The plan wants every directory to exist up front so none needs creating mid-build. Three were missing:

Rather than empty .gitkeep files, each got a README naming what lands there and on which day — internal/platform for auth, authz, tenant and audit (Days 3–4), internal/modules for the five-file domain pattern (Day 6+), deploy for Caddy and the Dockerfile (Day 14). Git needs a file to track a directory anyway; making it a useful one costs nothing.

The README previously described a single-surface employees app. It now opens with the three portals, and documents the envelope contract and the full kind-to-status table, since that is what anyone writing a handler needs on hand.

What Day 1 still leaves open

One structural question is deliberately unanswered here, because it is yours to decide.

The cost is not the move — it is the translation tax. The plan's prompts are written to be pasted as-is, and they name paths like internal/modules/hr. With Go under api/, every prompt from Day 6 to Day 14 needs editing before use, and every reply comes back with paths that do not match your tree.

Moving now is roughly half a day: one module path change, mechanical import rewrites, and updates to make.ps1, launch.json and sqlc.yaml. Git records it as renames, so history survives. After Day 5, with 31 pages and 35 tables in place, it is a much larger job.

Day 2 is the next hard dependency either way: the full table set, organization_id on every business table, and the transaction manager. Multi-tenancy does not exist yet, and the plan is right that retrofitting it later is the one mistake that genuinely costs time.
