Starting the database by hand

The build manual ends with a folder full of code. This one covers what you do every day after that: bringing Docker and Postgres up, applying the schema, proving the connection works, and pointing a GUI client at it.

Port 5434 is not the Postgres default, and that is deliberate. On this machine 5432 belongs to a Postgres running directly on Windows, and 5433 belongs to the ebike stack's container. A second service cannot bind a port that is already taken, so office360 claims the next free one. Check before you assume — see step 1.

1

Start Docker, and check the port

Launch Docker Desktop from the Start menu and wait for the whale icon in the system tray to stop animating. Then confirm the daemon is actually accepting commands:

An error mentioning dockerDesktopLinuxEngine means the daemon is still starting — wait and retry. Now check nothing already owns your port:

False is what you want — the port is free. If it returns True, something is already there. Find out what:

Skipping this check costs an hour. Docker reports a port clash as bind: address already in use, which reads like a Docker fault rather than "another project already has that port". If it happens, pick a free port and change it in three places: POSTGRES_PORT, the host half of DATABASE_URL, and the default in docker-compose.yml.

4

Prove the connection works

Three checks, cheapest first. A psql shell straight inside the container:

Type \dt to list tables, \q to quit. That proves Postgres itself is fine. Next, prove the API can reach it — start the server in one terminal:

A healthy response is {"status":"ok","db":"up","env":"development"}. If db reads down, the API is running but cannot reach Postgres — check the port in .env against what docker ps reports.

The server pings the database at boot and refuses to start if it cannot connect, so reaching the listening log line already tells you the connection is good.

Connecting a GUI client

DBeaver, pgAdmin, TablePlus, and the SQLTools extension in VS Code all want the same five fields.

FieldValue
Hostlocalhost
Port5434 — not 5432
Databaseoffice360
Usernameoffice360
Passwordoffice360_dev
SSL modedisable

The port is where this goes wrong. Every client defaults to 5432, and on this machine 5432 is a different Postgres entirely — so leaving the default gives you a successful connection to the wrong database, with none of your tables in it. If a client connects but shows nothing familiar, check the port before anything else.

Everyday commands

TaskCommand
Start./make.ps1 up
Stop (keeps data)./make.ps1 down
Apply migrations./make.ps1 migrate
Undo last migration./make.ps1 rollback
psql shell./make.ps1 psql
Watch the logsdocker compose logs -f postgres
Is it running?docker ps
Wipe everything./make.ps1 nuke — destroys the volume

down and nuke are not the same. down removes the container but leaves the volume, so your data comes back when you start again. nuke — and its underlying docker compose down -v — deletes the volume permanently. After a nuke you must re-run migrate, because the database is genuinely empty again.

Restarting Docker Desktop or rebooting stops the container but never touches the volume. Just run ./make.ps1 up again; your data is still there.

When it will not connect

SymptomCause and fix
failed to connect to the docker APIDocker Desktop is not running. Start it and wait for the tray icon to settle.
bind: address already in useAnother service owns the port. docker ps to find it, then pick a free port and change it in all three places.
connection refused, right after upContainer is up but Postgres is still initialising. Wait for healthy.
API exits at startupIt pings at boot by design. Either the container is down or DATABASE_URL is wrong.
healthz says "db":"down"API is up, Postgres is not reachable. Compare the port in .env with docker ps.
relation "employees" does not existMigrations never ran on this volume. ./make.ps1 migrate.
GUI connects but tables are missingYou are on 5432 — a different Postgres. Change the port to 5434.
password authentication failed.env and the volume disagree. Credentials are baked in at volume creation, so changing the password later needs a nuke.
All data vanishedSomething ran down -v or nuke. Re-run migrate.
make.ps1 parse errorsA non-ASCII character crept into the script. PowerShell 5.1 reads .ps1 as Windows-1252, and a UTF-8 em dash decodes into a smart quote that breaks every string after it. Keep the file pure ASCII.
