# office360

Multi-tenant ERP for Indian business operations — Go API + SvelteKit web app on PostgreSQL 16.

## Three portals

| Portal | Route | Who | Sees |
| --- | --- | --- | --- |
| **Super Admin** | `/platform` | Tech360 staff | Every organisation — health, provisioning, audit, plans, platform users |
| **Admin** | `/app` | Customer operators | One organisation — people, delivery, revenue, finance, operations, insight |
| **Client** | `/portal` | Customer's clients | Their own records only — projects, invoices, tickets, approvals |

Isolation between them is enforced in the service layer, not the UI. A record
outside the caller's organisation returns **404, never 403** — a 403 would
confirm the record exists.

## Stack

| Layer | Choice |
| --- | --- |
| API | Go 1.23 · [chi](https://github.com/go-chi/chi) v5 · [pgx](https://github.com/jackc/pgx) v5 |
| Queries | [sqlc](https://sqlc.dev) — SQL in, type-safe Go out. No ORM |
| Migrations | [golang-migrate](https://github.com/golang-migrate/migrate) |
| Database | PostgreSQL 16 (Docker) |
| Web | SvelteKit 2 · Svelte 5 (runes) · TypeScript · Vite |

## Prerequisites

Go 1.23+, Node 20+, and Docker Desktop. One Go tool, needed only when you change
the SQL:

```bash
go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest
```

Migrations run through `./cmd/migrate`, so the golang-migrate CLI is not
required.

## First run

```bash
cp .env.example .env
```

Then from the repo root in PowerShell:

```bash
./make.ps1 up
```

```bash
./make.ps1 migrate
```

Start the API, and the web app in a second terminal:

```bash
./make.ps1 api
```

```bash
./make.ps1 web
```

API on <http://localhost:8080>, web on <http://localhost:5173>.

> Postgres binds host port **5434**, not 5432, so this stack coexists with the
> other Postgres instances on this machine. Change `POSTGRES_PORT` in `.env` if
> you prefer.

## API conventions

**Every** response is enveloped. Success:

```json
{ "data": { }, "meta": { "request_id": "...", "total": 1, "limit": 50, "offset": 0 } }
```

Failure:

```json
{ "error": { "kind": "validation", "message": "...", "code": "...", "fields": { } },
  "meta": { "request_id": "..." } }
```

Handlers **never choose a status code**. They return a typed error from
`internal/httpx` and one map decides the status:

| Kind | Status | Means |
| --- | --- | --- |
| `validation` | 400 | Malformed or missing input |
| `unauthenticated` | 401 | Missing, expired or invalid credential |
| `forbidden` | 403 | Authenticated but not permitted |
| `not_found` | 404 | No such resource — also used to hide other tenants' records |
| `method_not_allowed` | 405 | Known path, wrong verb |
| `conflict` | 409 | Collides with existing state |
| `rule_violation` | 422 | Valid input a business rule rejects |
| `rate_limited` | 429 | Slow down |
| `internal` | 500 | Unexpected — cause is logged, never returned |

`code` is stable and machine-readable (`employee.email_taken`); branch on it
rather than on the message. `fields` carries per-field validation messages.

## Multi-tenancy

`organizations` is the tenant root and every business table carries
`organization_id`. Isolation is enforced by the schema, not by remembering a
`WHERE` clause:

- `organization_id uuid NOT NULL`, first column of every new business table.
- **Unique constraints are scoped to the organisation.** Two organisations may
  each have a Finance department and may each employ the same email address.
- **Foreign keys between business tables are composite,** carrying
  `organization_id`, so a row cannot reference another tenant's row.
- **Every query takes `organization_id`** — writes included. An UPDATE matching
  on `id` alone reaches across tenants.

Until Day 3 adds login, the organisation travels in an `X-Organization-Id`
header, resolved in one place (`internal/httpapi/tenant.go`) and failing closed:
no header means 401 and no query runs. The web app sends it from
`PUBLIC_DEV_ORGANIZATION_ID`; by hand you must set it yourself.

```bash
Invoke-RestMethod -Uri http://localhost:8080/api/v1/departments -Method Post -ContentType 'application/json' -Headers @{'X-Organization-Id' = '00000000-0000-0000-0000-000000000001'} -Body '{"name":"Finance"}'
```

That UUID is the "Default Organisation" seeded by migration `000002`.

## Transactions

Services own the transaction; handlers never see one. `internal/platform/txn`
provides `InTx` for writes and `InReadOnlyTx` for reads that must agree with each
other — a list and its total, which otherwise disagree if a row is inserted
between the two statements.

Inside the callback use only the `*db.Queries` you are handed. The manager's
`Queries()` runs on a different pooled connection, outside the transaction.

## Changing the data model

The migrations are the schema sqlc reads, so the order matters:

1. New migration pair in `internal/db/migrations/` (`000002_thing.up.sql` + `.down.sql`).
2. Add or edit queries in `internal/db/query/`.
3. `./make.ps1 sqlc` — regenerates `internal/db`.
4. `./make.ps1 migrate` — applies it locally.
5. Handlers, and routes in `internal/httpapi/server.go`.
6. Mirror the JSON shape in `web/src/lib/types.ts`, add a call in `web/src/lib/api.ts`.

Never hand-edit the generated `.go` files in `internal/db/` — they are
regenerated. The `migrations/` and `query/` subdirectories are yours.

## Environment

One `.env` at the repo root serves both apps. The Go side loads it via godotenv;
Vite reads it because `vite.config.ts` sets `envDir: '..'`.

The server **refuses to start** without `DATABASE_URL`, or without a
`JWT_SECRET` of at least 32 characters. Generate a real one per environment:

```bash
openssl rand -base64 48
```

`PUBLIC_DEV_ORGANIZATION_ID` tells the web app which organisation to act as. It
exists only until Day 4 moves the organisation onto the session token. Leaving it
unset does not break the build — every API call simply returns 401, because the
API fails closed rather than falling back to a default.

## Where this is

Day 1 is complete: toolchain, repository, folder tree, server foundation with
envelopes and typed errors, health and ping.

Day 2 is complete: multi-tenancy, the transaction manager, and the full schema —
41 tables, 38 of them tenant-scoped, across identity, people, payroll, clients,
delivery, revenue, finance and operations.

Verified against Postgres 16.14. Cross-tenant reads, updates and deletes all
return 404 with a second organisation present, and a schema audit confirms every
foreign key into a tenant table carries `organization_id`.

One caveat worth knowing: the table set in migration `000003` was derived from
the module names in this README, not from the build plan. Table and column names
may need correcting against it. The tenancy conventions above hold regardless,
which is the part that is expensive to change later.

Still absent: authentication (Day 3), the `authz`/`tenant`/`audit` packages and
the automated isolation test (Day 4), and every business module (Day 6+). The
organisation currently arrives as a request header, not a verified token — this
is not an access-controlled system yet.
